# Azure Cloud Security Operations
A cloud operations and monitoring platform built around the Utility Hub workload.

This project adds an operational security layer around the Utility Hub workload for observing application 

behaviour, detecting failures, investigating incidents, and responding

through Azure Monitor.

The application itself remains intentionally simple and unchanged. The focus of this project is the cloud

operations layer around the workload.

## Observe -> Detect -> Investigate -> Respond
The project follows a simple operational workflow:
    Application activity
            |
            v
          Observe
            |
            v
          Detect
            |
            v
       Investigate
            |
            v
         Respond

### Observe
Application telemetry is collected through Azure Application Insights and stored in the Log Analytics workspace.

The application also produces a structured application event when a calculator request is rejected because of an

invalid operation or input.

### Detect
Azure Monitor uses a scheduled query alert to detect failed HTTP requests.

When the query detects a failure, the alert fires and invokes an Azure Monitor Action Group.

### Investigate
KQL queries are used to investigate:

â€¢ Request volume and success/failure rates

â€¢ Failed HTTP requests

â€¢ Structured application rejection events

â€¢ Application exceptions

â€¢ Dependency failures

### Respond
The project uses an email Action Group for operational notification.

The response process is intentionally manual. Investigation and remediation are performed by an operator rather

than through automated remediation.

## Incident Simulation
A controlled application failure was generated by submitting an unsupported calculator operation.

Example request:

    {
      "operation":"invalid-operation",
      "a":10,
      "b":5
    }

The application returned:

HTTP 400 Bad Request

The application also generated a structured telemetry event:

calculator\_request\_rejected

The event included information such as:

â€¢ operation

â€¢ rejection reason

â€¢ logger name

â€¢ event name

The event was subsequently visible in the AppTraces table in Log Analytics.

This provided a complete investigation path:

## Operations Workbook

## Alerting
The project contains an Azure Monitor scheduled query alert for failed requests.

The alert:

â€¢ Evaluates every 5 minutes

â€¢ Uses a 5-minute evaluation window

â€¢ Fires when at least one failed request is detected

â€¢ Uses severity level 2

â€¢ Sends notifications through an Action Group

â€¢ Uses a common alert schema for the email receiver

A controlled HTTP 400 incident was used to verify that the alert could transition into a fired state.

## Application Monitoring
The FastAPI application uses Microsoft's Azure Monitor OpenTelemetry integration.

The Application Insights connection string is supplied to the App Service through an application setting rather

than storing it in the application source code.

This keeps telemetry configuration separate from application logic.

## CI/CD
GitHub Actions is used for deployment.

The workflow:

1\. Checks out the repository

2\. Sets up Python 3.12

3\. Installs dependencies

4\. Runs the automated test suite

5\. Authenticates to Azure using GitHub OIDC

6\. Deploys the application to Azure App Service

The deployment identity is dedicated to this project and scoped to the project's App Service.

No long-lived Azure client secret is stored in the repository.

## Cost Considerations
This project was deliberately designed to demonstrate cloud operations without introducing unnecessary

infrastructure.

The main continuously running compute resource is the B1 App Service plan.

Monitoring resources are configured with a 30-day retention period.

Additional services such as Azure Firewall, VPN Gateway, Sentinel/SOAR automation, or other continuously

running infrastructure were intentionally not introduced because they are not required to demonstrate the

operational monitoring objectives of this project.

## Lessons Learned
This project demonstrated several practical cloud operations concepts:

â€¢ Application telemetry needs to be designed, not simply enabled.

â€¢ Workspace-based Application Insights uses Log Analytics tables such as `AppRequests`, `AppTraces`,

`AppExceptions`, and `AppDependencies`.

â€¢ Structured application logging makes incident investigation significantly easier.

â€¢ Alerts need to be tested with controlled failures rather than assumed to work.

â€¢ Platform-generated requests can create operational noise and may need to be distinguished from application

failures.

â€¢ Monitoring configuration can be treated as infrastructure and managed through Terraform.

â€¢ Detection and investigation are different stages of an operational workflow.
