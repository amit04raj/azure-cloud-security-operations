Azure Cloud Security Operations

A cloud operations and monitoring platform built around the Utility Hub workload.

This project takes the same Utility Hub application used in the earlier portfolio projects and adds an operational

security layer for observing application behaviour, detecting failures, investigating incidents, and responding

through Azure Monitor.

The application itself remains intentionally simple and unchanged. The focus of this project is the cloud

operations layer around the workload.

Observe

Application telemetry is collected through Azure Application Insights and stored in the Log Analytics workspace.

The application also produces a structured application event when a calculator request is rejected because of an

invalid operation or input.

Detect

Azure Monitor uses a scheduled query alert to detect failed HTTP requests.

When the query detects a failure, the alert fires and invokes an Azure Monitor Action Group.

Investigate

KQL queries are used to investigate:

• Request volume and success/failure rates

• Failed HTTP requests

• Structured application rejection events

• Application exceptions

• Dependency failures

Respond

The project uses an email Action Group for operational notification.

The response process is intentionally manual. Investigation and remediation are performed by an operator rather

than through automated remediation.

Incident Simulation

A controlled application failure was generated by submitting an unsupported calculator operation.

Example request:

{

"operation":"invalid-operation",

"a":10,

"b":5

}

The application returned:

HTTP 400 Bad Request

The application also generated a structured telemetry event:

calculator\_request\_rejected

The event included information such as:

• operation

• rejection reason

• logger name

• event name

The event was subsequently visible in the AppTraces table in Log Analytics.

KQL Investigation

The repository contains reusable investigation queries under kql/.

Request overview

01-request-overview.kql

Provides:

• Total requests

• Successful requests

• Failed requests

• Average request duration

• P95 request duration

Failed requests

02-failed-requests.kql

Lists failed HTTP requests and provides:

• Timestamp

• HTTP result code

• Request name

• URL

• Duration

• Success status

Application events

03-application-events.kql

Searches for the structured calculator\_request\_rejected event.

Exceptions

04-exceptions.kql

Queries application exceptions recorded by Application Insights.

Dependency failures

05-dependencies.kql

Searches for unsuccessful or failed dependencies.

Operations Workbook

An Azure Monitor workbook named Cloud Security Operations provides a consolidated operational view.

The workbook contains five investigation panels:

1\. Request Overview

2\. Failed Requests

3\. Application Rejection Events

4\. Application Exceptions

5\. Dependency Failures

The workbook is managed through Terraform so that the monitoring configuration remains reproducible.

Alerting

The project contains an Azure Monitor scheduled query alert for failed requests.

The alert:

• Evaluates every 5 minutes

• Uses a 5-minute evaluation window

• Fires when at least one failed request is detected

• Uses severity level 2

• Sends notifications through an Action Group

• Uses common alert schema for the email receiver

A controlled HTTP 400 incident was used to verify that the alert could transition into a fired state.

Infrastructure

The Azure infrastructure is managed with Terraform.

Core resources include:

• Resource Group

• Linux App Service Plan

• Linux Web App

• Log Analytics Workspace

• Application Insights

• Azure Monitor Action Group

• Azure Monitor scheduled query alert

• Azure Monitor Workbook

The project uses a separate resource group and Terraform state from the other portfolio projects.

Application Monitoring

The FastAPI application uses Microsoft's Azure Monitor OpenTelemetry integration.

The Application Insights connection string is supplied to the App Service through an application setting rather

than being stored in the application source code.

This keeps telemetry configuration separate from application logic.

CI/CD

GitHub Actions is used for deployment.

The workflow:

1\. Checks out the repository

2\. Sets up Python 3.12

3\. Installs dependencies

4\. Runs the automated test suite

5\. Authenticates to Azure using GitHub OIDC

6\. Deploys the application to Azure App Service

The deployment identity is dedicated to this project and scoped to the project's App Service.

No long-lived Azure client secret is stored in the repository.

Security Considerations

The project demonstrates several operational security practices:

• HTTPS-only App Service

• TLS 1.2 minimum

• Disabled FTP basic authentication

• Disabled Web Deploy basic authentication

• OIDC authentication for CI/CD

• Dedicated deployment identity

• Resource-level RBAC scope for deployment

• Centralized application telemetry

• Structured application security/operations events

• Alert-driven detection

• Manual incident investigation

Cost Considerations

This project was deliberately designed to demonstrate cloud operations without introducing unnecessary

infrastructure.

The main continuously running compute resource is the B1 App Service plan.

Monitoring resources are configured with a 30-day retention period.

Additional services such as Azure Firewall, VPN Gateway, Sentinel/SOAR automation, or other continuously

running infrastructure were intentionally not introduced because they are not required to demonstrate the

operational monitoring objectives of this project.

Project Boundary

This project focuses on:

• Monitoring

• Observability

• Detection

• KQL investigation

• Alerting

• Operational notification

• Manual incident investigation

• Operational dashboards/workbooks

The following are intentionally outside the scope of this project:

• Automated remediation

• Automated resource isolation

• Microsoft Sentinel/SOAR workflows

• Policy-as-code governance

• Advanced zero-trust architecture

• Advanced identity architecture

• Automated security response

Those capabilities belong to the later advanced cloud security architecture stage of the portfolio.

Lessons Learned

This project demonstrated several practical cloud operations concepts:

• Application telemetry needs to be designed, not simply enabled.

• Workspace-based Application Insights uses Log Analytics tables such as `AppRequests`, `AppTraces`,

`AppExceptions`, and `AppDependencies`.

• Structured application logging makes incident investigation significantly easier.

• Alerts need to be tested with controlled failures rather than assumed to work.

• Platform-generated requests can create operational noise and may need to be distinguished from application

failures.

• Monitoring configuration can be treated as infrastructure and managed through Terraform.

• Detection and investigation are different stages of an operational workflow.
